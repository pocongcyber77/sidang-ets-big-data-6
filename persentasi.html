Ringkasan Sistem Satu Menit

AirQuality Alert adalah pipeline Big Data yang mengalirkan data kualitas udara dan berita lingkungan dari sumber eksternal sampai dashboard web.

  • producer_api.py mengambil AQI dari AQICN atau simulator. Producer dapat dibayangkan seperti petugas lapangan yang mengambil data dari sumber, lalu mengirimkannya ke jalur distribusi.
  • producer_rss.py mengambil berita dari RSS, membersihkan summary, dan mencegah duplikasi. RSS di sini berperan seperti daftar berita langganan yang dicek berkala.
  • Kafka memisahkan producer dari consumer melalui dua topic: airquality-api dan airquality-rss. Kafka dapat dianalogikan sebagai ruang tunggu pesan, sedangkan topic adalah rak atau jalur khusus untuk jenis pesan tertentu.
  • consumer_to_hdfs.py membaca Kafka, melakukan buffer, menulis data ke HDFS, dan membuat mirror JSON untuk dashboard. Consumer adalah pihak yang mengambil pesan dari ruang tunggu, buffer adalah wadah sementara, dan mirror JSON adalah salinan kecil agar dashboard cepat membaca data terbaru.
  • HDFS menyimpan raw data dan hasil Spark di /data/airquality. HDFS adalah gudang penyimpanan besar, raw data adalah data mentah sebelum diringkas, dan hasil Spark adalah data yang sudah dianalisis.
  • spark/analysis.ipynb menghitung tiga analisis utama. Spark berperan seperti mesin pengolah data besar yang mengubah data mentah menjadi insight.
  • dashboard/app.py menyajikan JSON ke frontend. JSON adalah format pertukaran data yang mudah dibaca program, sedangkan frontend adalah bagian tampilan yang dilihat pengguna.
  • index.html dan style.css menampilkan dashboard yang auto-refresh. Auto-refresh berarti halaman memperbarui isi secara otomatis tanpa pengguna menekan tombol refresh manual.

Contoh:

Flush terjadi jika BUFFER_MAX_RECORDS tercapai atau BUFFER_FLUSH_SEC tercapai. Flush berarti proses mengosongkan buffer, yaitu wadah sementara yang menampung data sebelum ditulis permanen. BUFFER_MAX_RECORDS adalah batas jumlah data dalam wadah, sedangkan BUFFER_FLUSH_SEC adalah batas waktu menunggu. Jadi sistem tidak menulis satu per satu, tetapi menunggu sampai data cukup banyak atau waktu tunggunya habis, seperti mengirim paket secara rombongan agar lebih efisien.

Istilah Penjelasan Teknis Penjelasan Non-Teknis untuk Presentasi
AQI Air Quality Index, angka indeks kualitas udara. Nilai ringkas untuk menunjukkan udara sedang baik, sedang, atau buruk. Semakin tinggi angkanya, semakin perlu diwaspadai.
API Antarmuka untuk mengambil data dari sistem lain. Seperti loket resmi yang menyediakan data dengan format tertentu. Program kita bertanya ke loket itu, lalu menerima jawaban.
RSS Format feed berita yang bisa dibaca otomatis. Seperti daftar langganan berita. Sistem mengecek daftar itu secara berkala tanpa membuka situs satu per satu.
Producer Program yang mengambil data lalu mengirimkannya ke Kafka. Seperti kurir awal yang mengambil paket dari sumber dan meletakkannya di ruang tunggu.
Consumer Program yang membaca pesan dari Kafka lalu memprosesnya. Seperti petugas penerima paket yang mengambil paket dari ruang tunggu dan menyimpannya ke gudang.
Kafka Message broker untuk menampung aliran pesan. Seperti terminal atau ruang tunggu pesan agar pengirim dan penerima tidak harus bekerja pada detik yang sama.
Topic Kanal pesan di Kafka. Seperti rak berbeda untuk jenis paket berbeda. Data AQI masuk rak AQI, berita masuk rak RSS.
Message Satu unit data yang dikirim ke Kafka. Seperti satu paket kecil berisi informasi kota, nilai AQI, waktu, atau berita.
Key Identitas pembeda pada message Kafka. Seperti label pada paket. Misalnya city_slug membuat data Surabaya punya label yang konsisten.
Buffer Penampung sementara sebelum data ditulis permanen. Seperti keranjang sementara. Data dikumpulkan dulu supaya penulisan ke gudang tidak terlalu sering.
Flush Proses mengirim isi buffer ke penyimpanan. Seperti mengosongkan keranjang ke gudang. Setelah keranjang cukup penuh atau waktu tunggu habis, isinya disimpan.
Batch Sekelompok data yang diproses bersama. Seperti mengirim banyak paket sekali jalan agar lebih efisien daripada mengirim satu per satu.
Commit offset Menandai pesan Kafka sudah berhasil diproses. Seperti memberi tanda centang bahwa paket sudah aman sampai gudang. Jika belum aman, jangan dicentang dulu.
Offset Posisi pesan terakhir yang dibaca di Kafka. Seperti nomor antrean terakhir yang sudah dilayani.
HDFS Hadoop Distributed File System, penyimpanan data terdistribusi. Seperti gudang besar yang dapat menyimpan data historis dalam jumlah banyak.
DataNode Node penyimpan data di HDFS. Seperti rak atau cabang gudang tempat potongan data disimpan.
NameNode Pengatur lokasi file di HDFS. Seperti kepala gudang yang tahu file ada di rak mana.
NDJSON Format file berisi satu JSON per baris. Seperti buku catatan; setiap baris adalah satu kejadian data, sehingga mudah dibaca bertahap.
Parquet Format penyimpanan kolom untuk analitik. Seperti arsip yang disusun rapi per kolom sehingga mesin analisis lebih cepat membaca bagian yang dibutuhkan.
Spark Mesin pemrosesan data besar. Seperti dapur analitik yang mengolah data mentah menjadi ringkasan, peringkat, dan pola.
DataFrame Struktur tabel di Spark. Seperti spreadsheet besar berisi baris dan kolom, tetapi diproses oleh mesin data.
Temp View Tampilan sementara agar DataFrame bisa di-query dengan SQL. Seperti memberi nama sementara pada tabel agar mudah ditanya dengan bahasa query.
SQL Bahasa query untuk mengambil dan menghitung data. Seperti bahasa bertanya ke tabel: rata-ratanya berapa, kelompoknya apa, urutannya bagaimana.
Endpoint Alamat API yang bisa dipanggil frontend. Seperti alamat loket tertentu. /api/data adalah loket untuk mengambil data dashboard.
Frontend Bagian aplikasi yang dilihat pengguna. Tampilan dashboard di browser: kartu, grafik, warna, dan teks.
Backend Bagian aplikasi yang menyiapkan data untuk frontend. Dapur belakang yang membaca file, menyusun response, lalu mengirimkannya ke tampilan.
Fallback Jalur cadangan ketika jalur utama gagal. Seperti ban serep. Jika API atau akses utama bermasalah, sistem tetap bisa berjalan dengan cara alternatif.
Mirror JSON Salinan data ringkas dalam file JSON lokal. Seperti fotokopi data terbaru agar dashboard cepat membaca tanpa membuka gudang besar langsung.

Tujuan Diagram

Diagram ini adalah peta utama seluruh sistem. Diagram ini menjelaskan semua lapisan dari sumber data sampai dashboard yang dibuka pengguna.

Penjelasan Semua Kotak

Kotak / Node Penjelasan
Sumber Data Eksternal Berisi AQICN API, Simulator AQI, dan RSS Feeds. AQICN adalah sumber data kualitas udara nyata. Simulator adalah cadangan jika token kosong atau API gagal. RSS Feeds adalah sumber konteks berita dari Detik, Tempo, dan Kompas.
Lapisan Ingestion Python Berisi producer_api.py dan producer_rss.py. Ingestion berarti tahap memasukkan data ke sistem; secara sederhana ini adalah pintu masuk yang mengambil data dari luar, membentuk payload JSON, lalu mengirimkannya ke Kafka.
Apache Kafka Berisi topic airquality-api dan airquality-rss. Kafka menjadi antrian data agar producer tidak langsung bergantung pada HDFS atau dashboard; bayangkan Kafka sebagai ruang tunggu pesan agar pengirim dan penerima tidak harus aktif pada waktu yang sama.
Consumer dan Sink Berisi consumer_to_hdfs.py dan mirror dashboard/data. Consumer membaca Kafka, melakukan buffer, menulis ke HDFS, dan membuat file JSON lokal untuk dashboard. Sink berarti tujuan akhir penulisan data, seperti saluran pembuangan yang mengarahkan data ke tempat penyimpanan.
Hadoop HDFS Berisi path /data/airquality/api, /data/airquality/rss, dan /data/airquality/hasil. Ini adalah gudang data historis yang menyimpan catatan lama, bukan hanya data terbaru.
Apache Spark Berisi spark/analysis.ipynb dan spark_results.json. Spark membaca data historis dari HDFS, menghitung analisis, lalu menulis hasil; secara non-teknis Spark adalah mesin pengolah yang membuat data mentah menjadi ringkasan yang bisa dipahami.
Presentation Layer Berisi dashboard/app.py, index.html + style.css, dan browser pengguna. Layer ini mengubah data hasil pipeline menjadi halaman dashboard, yaitu bagian yang akhirnya dilihat manusia.

Penjelasan Semua Flow

  • AQICN dan Simulator mengarah ke producer_api.py karena keduanya adalah sumber alternatif untuk data AQI. AQICN adalah sumber nyata, sedangkan simulator adalah sumber tiruan yang menjaga demo tetap berjalan.
  • RSS Feeds mengarah ke producer_rss.py karena berita memiliki bentuk data berbeda dari AQI, sehingga perlu jalur pengolahan sendiri.
  • Dua producer mengarah ke topic Kafka yang berbeda agar aliran angka AQI dan aliran berita tidak bercampur. Topic dapat dijelaskan sebagai jalur antrean terpisah.
  • Dua topic Kafka mengarah ke consumer_to_hdfs.py karena satu consumer membaca kedua topic dengan dua thread. Thread berarti jalur kerja paralel di dalam satu program, seperti dua petugas yang bekerja bersamaan.
  • Consumer mengarah ke HDFS dan mirror dashboard karena ia menulis data historis sekaligus snapshot cepat. Snapshot berarti salinan keadaan terbaru pada saat tertentu.
  • Spark membaca HDFS API, lalu menulis hasil ke HDFS hasil dan spark_results.json. Artinya data mentah dari gudang diolah menjadi hasil ringkas untuk analisis dan dashboard.
  • Flask membaca mirror live dan hasil Spark, lalu frontend mengambil data dari Flask. Flask berperan sebagai pelayan data, sedangkan frontend adalah layar yang memvisualisasikan data tersebut.

Narasi Presentasi

Inti diagram ini adalah pemisahan tanggung jawab. Producer mengambil data, Kafka menahan data seperti ruang tunggu, consumer menyimpan data, HDFS mengarsipkan data seperti gudang besar, Spark menganalisis data seperti mesin pengolah, dan dashboard menyajikan data dalam bentuk yang mudah dibaca manusia.

Kalimat presentasi yang disarankan:

Diagram ini menunjukkan bahwa sistem tidak dibuat sebagai satu program besar, tetapi sebagai rangkaian komponen dengan tugas masing-masing. Data kualitas udara dan berita diambil oleh producer, ditaruh dulu di Kafka sebagai antrian pesan, diambil consumer untuk disimpan ke HDFS sebagai gudang historis, lalu dianalisis Spark dan akhirnya ditampilkan di dashboard Flask agar bisa dibaca pengguna.

Tujuan Diagram

Diagram ini menjelaskan urutan kejadian saat data AQI dikirim ke Kafka.

Penjelasan Semua Kotak

Kotak / Node Penjelasan
Polling Timer Pemicu periodik berdasarkan POLL_INTERVAL_SEC, default 900 detik. Polling berarti program mengecek data secara berkala, seperti seseorang yang melihat termometer setiap beberapa menit.
producer_api.py Program utama yang mengatur pengambilan data AQI, fallback simulator, normalisasi field, dan pengiriman Kafka. Normalisasi field berarti menyamakan nama dan bentuk kolom agar data dari berbagai kondisi tetap rapi.
AQICN API Sumber data kualitas udara nyata jika token tersedia dan response valid. Token adalah kunci akses ke layanan API.
Simulator Sumber cadangan jika token kosong, request gagal, atau FORCE_SIMULATOR=1. Simulator membuat data tiruan yang masuk akal supaya alur sistem tetap dapat ditunjukkan.
Kafka topic airquality-api Topic tujuan untuk seluruh event AQI. Topic ini seperti jalur khusus untuk paket data kualitas udara.

Penjelasan Semua Flow

  • Timer memicu producer sesuai interval. Interval adalah jarak waktu antar pengecekan, sehingga sistem tidak terus-menerus meminta data tanpa jeda.
  • Producer melakukan loop untuk setiap kota: Surabaya, Malang, Sidoarjo, Gresik, dan Mojokerto. Loop berarti proses yang diulang untuk daftar kota satu per satu.
  • Producer mencoba request ke AQICN dengan slug kota. Request berarti permintaan data, sedangkan slug adalah nama kota dalam format alamat yang konsisten, misalnya tanpa spasi.
  • Jika AQICN sukses, payload dinormalisasi. Payload adalah isi data yang diterima, dan normalisasi berarti merapikan bentuknya agar kolomnya seragam.
  • Jika AQICN gagal, simulator membuat payload realistis. Ini menjaga presentasi tetap berjalan meskipun sumber eksternal bermasalah.
  • Producer menambahkan city, city_slug, dan timestamp_ingest. timestamp_ingest adalah waktu saat data masuk ke sistem, seperti stempel waktu penerimaan.
  • Producer mengirim message ke Kafka memakai key city_slug. Message adalah paket data, dan key adalah label paket agar data per kota mudah dikenali.
  • Setelah satu siklus, producer melakukan flush agar message benar-benar dikirim. Flush di producer berarti memastikan semua pesan yang masih tertahan di memori benar-benar keluar ke Kafka.

Ingestion AQI dirancang tahan gangguan. Demo tidak berhenti hanya karena API eksternal tidak tersedia.

Kalimat presentasi yang disarankan:

Pada bagian ini, producer API bekerja seperti petugas yang mengecek kualitas udara tiap kota secara berkala. Jika AQICN tersedia, sistem memakai data nyata; jika tidak, simulator menjadi cadangan. Setelah data dirapikan dan diberi label kota serta waktu masuk, data dikirim ke Kafka agar tahap berikutnya bisa mengambilnya tanpa harus bergantung langsung ke API eksternal.

Tujuan Diagram

Diagram ini menjelaskan bagaimana berita RSS dibaca, difilter, didedup, lalu dikirim ke Kafka.

Penjelasan Semua Kotak

Kotak / Node Penjelasan
Polling Timer Pemicu periodik berdasarkan POLL_INTERVAL_SEC_RSS, default 300 detik. Artinya berita dicek berkala, bukan hanya sekali saat program dinyalakan.
producer_rss.py Program yang membaca feed, membersihkan summary, menghitung hash link, dan mengirim message. Hash link adalah sidik jari unik dari URL berita agar berita yang sama mudah dikenali.
RSS Feed Sumber berita dari URL feed yang didefinisikan di default kode atau RSS_FEEDS. RSS feed dapat dipahami sebagai daftar berita yang disediakan situs untuk dibaca otomatis.

Penjelasan Semua Flow

  • Producer memuat seen_ids.json saat siklus dimulai. File ini seperti daftar ceklis berita yang sudah pernah dikirim.
  • Producer membaca setiap feed dengan feedparser. feedparser adalah library yang membantu membaca format RSS agar program tidak perlu membongkar teks mentah secara manual.
  • Setiap entry dibersihkan dari HTML dan dibuat ID berdasarkan MD5 link. HTML adalah format tampilan web, sedangkan MD5 di sini dipakai sebagai sidik jari pendek untuk membedakan URL berita.
  • Jika ID sudah ada, berita dilewati agar tidak duplikat. Duplikat berarti berita yang sama muncul lebih dari sekali.
  • Jika berita relevan dengan keyword, berita dikirim ke Kafka. Keyword adalah kata kunci seperti polusi, udara, atau lingkungan yang membantu memilih berita yang sesuai topik.
  • Jika tidak ada yang relevan, fallback Top-N dapat dikirim untuk menjaga dashboard tetap terisi. Top-N berarti mengambil beberapa berita teratas sebagai cadangan.
  • Setelah kirim, ID berita disimpan kembali secara atomic. Atomic berarti penyimpanan dilakukan secara utuh, sehingga file catatan tidak mudah rusak di tengah proses.

Narasi Presentasi

RSS ingestion menyeimbangkan relevansi dan kebutuhan demo. Sistem mencoba memilih berita lingkungan, tetapi tetap punya fallback agar panel berita tidak kosong.

Kalimat presentasi yang disarankan:

Pada jalur RSS, sistem bukan hanya mengambil semua berita mentah. Berita dibersihkan dari HTML, diberi ID unik dari link, dicek apakah sudah pernah muncul, lalu difilter berdasarkan kata kunci lingkungan. Jika tidak ada berita yang cocok, ada fallback Top-N agar dashboard tetap memiliki konteks berita saat demo.

sequenceDiagram
    autonumber
    participant KafkaAPI as topic airquality-api
    participant KafkaRSS as topic airquality-rss

    participant Buffer as In-memory Buffer

    participant Mirror as dashboard/data

        KafkaAPI->>Consumer: poll messages
        Consumer->>Buffer: append API records
    and Thread RSS
        KafkaRSS->>Consumer: poll messages
        Consumer->>Buffer: append RSS records
    end

        Consumer->>HDFS: write NDJSON batch
        Consumer->>Mirror: update live_api/live_rss
        Consumer->>KafkaAPI: commit offset
        Consumer->>KafkaRSS: commit offset
    else BUFFER_FLUSH_SEC tercapai
        Consumer->>HDFS: write NDJSON batch
        Consumer->>Mirror: update live_api/live_rss
        Consumer->>KafkaAPI: commit offset
        Consumer->>KafkaRSS: commit offset
    else HDFS write gagal
        Consumer->>Buffer: pertahankan buffer
        Consumer-->>KafkaAPI: offset belum commit
        Consumer-->>KafkaRSS: offset belum commit
    end

Tujuan Diagram

Diagram ini menjelaskan bagaimana consumer membaca dua topic Kafka dan menyimpan data dengan aman.

Penjelasan Semua Kotak

Kotak / Node Penjelasan
topic airquality-api Topic berisi event AQI. Topic ini adalah jalur antrean khusus untuk data angka kualitas udara.
topic airquality-rss Topic berisi event RSS. Topic ini adalah jalur antrean khusus untuk berita agar tidak bercampur dengan data AQI.
consumer_to_hdfs.py Consumer yang menjalankan dua thread, satu untuk API dan satu untuk RSS. Dua thread berarti dua jalur kerja berjalan paralel agar kedua jenis data bisa diproses bersamaan.
In-memory Buffer Tempat menampung record sementara sebelum ditulis sebagai batch. In-memory berarti disimpan sementara di memori program, seperti keranjang sementara sebelum barang dipindahkan ke gudang.
Hadoop HDFS Tujuan penyimpanan historis. HDFS adalah gudang besar untuk menyimpan data dalam jangka panjang.
dashboard/data Tujuan mirror JSON untuk dashboard. Mirror JSON adalah salinan kecil data terbaru agar dashboard tidak perlu membaca HDFS langsung.

Penjelasan Semua Flow

  • Thread API membaca topic airquality-api. Thread dapat dijelaskan sebagai jalur kerja di dalam program yang fokus pada data AQI.
  • Thread RSS membaca topic airquality-rss. Jalur ini dipisahkan agar berita tetap diproses meskipun aliran AQI sedang ramai.
  • Record dari dua aliran masuk ke buffer masing-masing. Record berarti satu baris atau satu kejadian data; buffer adalah wadah sementara sebelum data dipindahkan ke penyimpanan tetap.
  • Flush terjadi jika BUFFER_MAX_RECORDS tercapai atau BUFFER_FLUSH_SEC tercapai. Flush berarti mengosongkan buffer ke penyimpanan. BUFFER_MAX_RECORDS adalah batas jumlah record dalam buffer, sedangkan BUFFER_FLUSH_SEC adalah batas waktu menunggu. Jadi data ditulis ketika keranjang sudah cukup penuh atau ketika waktu tunggu sudah habis.
  • Pada flush sukses, data ditulis ke HDFS sebagai NDJSON. NDJSON berarti setiap baris file adalah satu JSON, sehingga data mudah ditambahkan dan dibaca kembali secara bertahap.
  • Mirror dashboard diperbarui agar dashboard punya snapshot terbaru. Snapshot adalah salinan kondisi terkini yang cepat dibuka oleh halaman web.
  • Offset Kafka baru di-commit setelah write sukses. Offset adalah nomor posisi pesan di Kafka, sedangkan commit adalah tanda bahwa pesan sudah benar-benar aman diproses.
  • Jika write gagal, buffer dipertahankan dan offset tidak di-commit. Artinya sistem tidak berpura-pura berhasil; data tetap ditahan agar bisa dicoba lagi.

Narasi Presentasi

Desain commit setelah flush mencegah data dianggap selesai sebelum benar-benar tersimpan. Secara non-teknis, sistem baru memberi tanda centang ketika paket sudah sampai gudang, bukan saat paket baru diambil dari ruang tunggu.

Kalimat presentasi yang disarankan:

Bagian consumer ini penting karena menjelaskan keamanan penyimpanan data. Data dari Kafka tidak langsung dicentang selesai. Data masuk dulu ke buffer, lalu di-flush ke HDFS ketika jumlahnya cukup atau waktunya sudah habis. Setelah penulisan berhasil, barulah offset di-commit. Dengan cara ini, jika HDFS gagal ditulis, data belum dianggap selesai dan masih bisa diproses ulang.

Penjelasan Semua Flow

  • Browser memuat HTML. Ini adalah tahap halaman dasar dibuka oleh pengguna.
  • HTML memuat JavaScript dan CSS. JavaScript mengatur perilaku halaman, sedangkan CSS mengatur tampilan halaman.
  • JavaScript fetch /api/data. Fetch berarti browser meminta paket data terbaru ke backend Flask.
  • Endpoint Flask membaca JSON lokal dan fallback demo jika perlu. Flask mengambil data dari file ringkas, lalu memakai data contoh jika file runtime belum ada.
  • Response kembali ke JavaScript. Response adalah jawaban dari backend ke browser.
  • JavaScript merender panel Spark, API, RSS, dan chart. Render berarti menggambar data menjadi elemen visual seperti kartu, grafik, dan daftar berita.

Script Presentasi 7 Menit

Waktu Narasi
Menit 0-1 "Proyek ini adalah AirQuality Alert, yaitu sistem monitoring kualitas udara untuk wilayah Jawa Timur. Yang dimonitor bukan hanya angka AQI, tetapi juga konteks berita lingkungan. Secara teknis ini disebut pipeline Big Data, tetapi secara sederhana pipeline berarti jalur kerja berurutan: data diambil, ditampung, disimpan, dianalisis, lalu ditampilkan."
Menit 1-2 "Pada peta besar sistem, sumber data masuk melalui producer. Producer adalah program pengambil data. Data tidak langsung ditembak ke dashboard, tetapi masuk dulu ke Kafka. Kafka adalah ruang tunggu pesan agar pengambil data dan penyimpan data tidak saling bergantung. Setelah itu consumer mengambil pesan, menyimpannya ke HDFS sebagai gudang historis, Spark mengolahnya menjadi insight, dan dashboard menampilkannya ke pengguna."
Menit 2-3 "Pada topologi lokal, bagian infrastruktur seperti Kafka dan Hadoop berjalan di Docker. Docker bisa dipahami sebagai wadah terisolasi untuk menjalankan service berat. Sementara itu, program Python seperti producer, consumer, notebook Spark, dan Flask dashboard berjalan di host atau mesin lokal. Pemisahan ini membuat demo lebih mudah dikontrol dan arsitekturnya lebih rapi."
Menit 3-4 "Pada sequence AQI, program mengecek data setiap interval tertentu. Interval berarti jeda waktu pengecekan. Jika API AQICN berhasil, sistem memakai data nyata. Jika gagal, simulator menjadi fallback atau jalur cadangan. Pada sequence RSS, berita dibaca dari feed, dibersihkan dari HTML, diberi ID unik, lalu dicek supaya tidak duplikat. Jadi sistem tidak hanya mengambil data, tetapi juga menjaga data tetap relevan dan tidak berulang."
Menit 4-5 "Pada consumer ke HDFS, data dari Kafka masuk ke buffer terlebih dahulu. Buffer adalah keranjang sementara. Flush terjadi ketika keranjang penuh berdasarkan BUFFER_MAX_RECORDS atau waktu tunggunya habis berdasarkan BUFFER_FLUSH_SEC. Setelah flush berhasil, data ditulis ke HDFS dalam format NDJSON, yaitu satu JSON per baris. Offset Kafka baru di-commit setelah write sukses, artinya pesan baru diberi tanda selesai ketika benar-benar aman tersimpan."
Menit 5-6 "Pada Spark, data mentah dari HDFS dibaca sebagai DataFrame, yaitu tabel besar berisi baris dan kolom. Data kemudian dinormalisasi agar kolomnya seragam, lalu dibuat temp view supaya bisa dianalisis dengan SQL. Hasil analisisnya ada tiga: distribusi kategori AQI, rata-rata AQI per jam, dan ranking kota. Data contract memastikan semua komponen sepakat tentang nama field, seperti formulir standar yang harus diisi dengan format yang sama."
Menit 6-7 "Pada dashboard, Flask bertindak sebagai backend yang menyediakan endpoint /api/data. Endpoint adalah alamat untuk meminta data. Browser menjalankan HTML, CSS, dan JavaScript; JavaScript mengambil data secara berkala atau auto-refresh setiap 30 detik. State machine di akhir menunjukkan urutan demo yang benar: start stack, init infra, jalankan producer, jalankan consumer, tunggu HDFS menerima data, jalankan Spark, lalu buka dashboard untuk monitoring."

Hal yang Tidak Boleh Terlewat Saat Menjelaskan

  • Producer API dan RSS terpisah karena format data dan logika ingest berbeda. Data AQI berbentuk angka sensor, sedangkan RSS berbentuk berita teks, jadi cara membersihkan dan mengirimnya tidak sama.
  • Kafka punya dua topic agar data AQI dan berita tidak tercampur. Topic adalah jalur antrean, seperti rak berbeda untuk paket berbeda.
  • Consumer memakai dua thread agar dua topic dapat diproses paralel. Thread adalah jalur kerja di dalam program, sehingga data AQI dan RSS bisa ditangani bersamaan.
  • Offset Kafka baru di-commit setelah flush berhasil. Offset adalah nomor posisi pesan, commit adalah tanda selesai, dan flush adalah pemindahan isi buffer ke HDFS.
  • HDFS menyimpan data historis; dashboard tidak membaca HDFS langsung. HDFS berperan sebagai gudang besar, sedangkan dashboard butuh salinan ringkas agar cepat.
  • Mirror JSON dibuat untuk kebutuhan dashboard yang cepat. Mirror JSON adalah fotokopi data terbaru dalam ukuran kecil.
  • Spark membaca data historis, bukan data live langsung dari Kafka. Artinya Spark fokus menganalisis catatan yang sudah tersimpan, bukan mengejar pesan real-time satu per satu.
  • Notebook punya fallback untuk masalah akses HDFS di WSL2. Fallback adalah jalur cadangan agar analisis tetap bisa berjalan jika jalur utama bermasalah.
  • Dashboard punya fallback demo agar halaman tidak kosong. Ini penting untuk presentasi karena tampilan tetap bisa dijelaskan walaupun data runtime belum tersedia.
  • State machine menunjukkan urutan operasional demo yang benar. State machine adalah peta status dari sistem mati sampai sistem siap monitoring.

Penutup

Arsitektur AirQuality Alert menunjukkan alur Big Data yang lengkap: ingestion sebagai pintu masuk data, message broker sebagai ruang tunggu pesan, distributed storage sebagai gudang data besar, analytics sebagai proses mengubah data mentah menjadi insight, dan presentation sebagai tampilan akhir untuk pengguna. Setiap diagram dalam dokumen ini menjelaskan satu sudut pandang yang berbeda: peta besar, deployment, sequence runtime, struktur HDFS, analisis Spark, data contract, state machine, dan dashboard.

Dokumen ini dapat dipakai sebagai naskah presentasi, bahan penjelasan diagram, atau pendamping poster ARCHITECTURE_A1.md.
